# HR Suite — Fixes Applied 2026-07-04

Log of bugs found and fixed while working through `WORKFLOW_TESTING.md` (Tests 10–19). Covers what changed, why, and what's confirmed vs. still open.

## Code changes made

### 1. Duplicate `public/js` folder (root cause for Test 10/12/13)
The app had **two** `public/js` folders: the real one Frappe serves (`hr_suite/hr_suite/public/js/`) and an orphaned duplicate one level too deep (`hr_suite/hr_suite/hr_suite/public/js/`). Three files only existed in the dead folder and 404'd in every browser session:
- `work_permit_iqama.js` (Muqeem buttons on the Work Permit Iqama form)
- `nitaqat_record.js` (Qiwa "Sync from Qiwa" button)
- `wps_payroll.js` (Mudad/WPS buttons on Payroll Entry)

**Fix:** moved all three into the real `public/js/` folder, merged an improved `hr_suite.css` that had also been edited in the dead folder, then deleted the dead folder entirely. Confirmed via `bench build --app hr_suite` that all `doctype_js` targets in `hooks.py` now resolve to real files.

### 2. `"Work Permit / Iqama"` vs `"Work Permit Iqama"` doctype name mismatch
The real doctype is named `Work Permit Iqama` (no slash). Several places referenced it with a slash, which doesn't exist as a doctype — causing runtime errors when those code paths ran.
- `public/js/employee.js` (4 places) and `public/js/work_permit_iqama.js` (1 place, its `frappe.ui.form.on` registration — meant the whole Muqeem button group on that form never rendered at all).
- Fixed directly in the IDE.

### 3. `hrms.py` — `on_employee_separation_submit` / EOSB `calculation_notes` (Test 18)
`calculate_settlement()`'s Saudi branch returns a `"calculation_notes"` key; its AE/IN/BH/OM branches return a `"notes"` key. The auto-create code only read `result.get('notes', '')`, so the detailed breakdown was silently dropped for Saudi employees (the default/most common case).
**Fix:** read `result.get('notes') or result.get('calculation_notes') or ''`.

### 4. `hrms.py` — GPSSA/EPF/ESI deduction not reflected in Salary Slip totals (Test 14/15)
`before_salary_slip_submit` appends the deduction row in `before_submit`, which runs **after** HRMS already computed `net_pay`/`total_deduction` in `validate()`. The row was saved but excluded from totals — net pay looked unaffected even though a deduction existed.
**Fix:** added `doc.set_net_pay()` right after injecting the deduction, so totals recompute from the now-current deductions table.
**Live-confirmed:** AE employee, 15,000 AED basic → GPSSA 750 (5%) → `total_deduction=750`, `net_pay=14,250`. Correct.

### 5. `hrms.py` — EPF wage base used Salary Slip gross pay, not Basic (Test 15)
`basic = flt(doc.get("base_gross_pay") or get_employee_basic_salary_global(employee))` — `base_gross_pay` is total gross pay (all earnings), not the Basic component. Fine when Basic is the only earning (as in the test data), wrong the moment HRA/other allowances exist — would overstate the EPF wage base.
**Fix:** always use `get_employee_basic_salary_global(employee)` (reads Basic off the active Country Employment Contract / CTC), matching what every other statutory calc in the app already uses.

### 6. `hrms.py` — sick leave day-count excluded the current application (Test 15/16)
`on_leave_application_validate` summed *other* submitted sick-leave days but never added the current application's own day count before checking the pay-tier threshold — so the request that actually crosses a tier boundary (e.g. the 31st day) never got its own warning; it always warned one submission late.
**Fix:** `sick_days_used = sick_days_before + flt(doc.total_leave_days)`.

### 7. `hrms.py` / `end_of_service_benefit.json` — invalid EOSB `termination_reason` Select value (Test 14/18)
`reason_map` produces human-readable strings like `"Resignation by Employee"` for settlement-formula token matching, but the `End of Service Benefit.termination_reason` Select field only accepts `Resignation | Termination by Employer | End of Fixed Term | Dismissal | Death | Total Disability`. Inserting with the human-readable string threw a `ValidationError`, swallowed by a bare `except Exception`, so **no EOSB record was created at all** for resignations (the most common separation reason).
**Fix:** added a `_eosb_select_reason()` translation map applied only at insert time, and added `"Retirement"` as a valid Select option (it was missing entirely — `"Retired"` had nowhere valid to map to).
**Live-confirmed:** resignation now correctly creates an EOSB record with `termination_reason = "Resignation"`.

### 8. `hrms.py` — `payment_status` written to doctypes that don't have that field (Test 14/17)
`_ensure_epfesi_contribution` and `_ensure_statutory_contribution` both set `"payment_status": "Pending"`, but neither `EPF ESI Contribution` nor `Statutory Contribution` has that field (only `GOSI Contribution` does — those two are submittable doctypes that track status via `docstatus` instead). Frappe silently drops unknown dict keys, so this wasn't crashing anything, just dead/misleading code.
**Fix:** removed the invalid key from both.

### 9. `end_of_service_benefit.py` — **the big one**: EOSB always used the Saudi formula regardless of country (Test 14 step 6)
This was invisible to code review and only surfaced through live testing. `EndofServiceBenefit.validate()` unconditionally called `calculate_eosb_components()` (Saudi-only formula) inside `_calculate_eosb()`, **overwriting** whatever correct country-specific numbers `on_employee_separation_submit` had just computed via `calculate_settlement()`. Net effect: every EOSB record ever saved for a non-Saudi employee (AE/IN/BH/OM) silently got paid out using the wrong formula — the Settlement Estimate *preview* button showed the right country formula (it never saves a document, so never hit this code path), but the real saved record was always wrong.
**Fix:** `_calculate_eosb()` now resolves the employee's work country; Saudi employees keep the existing behavior unchanged, non-Saudi employees are routed through the correct country formula function (`_calculate_uae_gratuity` / `_calculate_india_gratuity` / `_calculate_bh_indemnity` / `_calculate_om_indemnity`) with results mapped onto the doctype's generic fields.
**Live-confirmed:** UAE employee, 6 years, resignation → `net_eosb` corrected from **65,041.10** (wrong, SA formula) to **67,541.10** (correct, Gratuity-AE formula, matches the Settlement Estimate preview exactly).

### 10. `public/js/employee.js` — GOSI Member Status dialog read wrong field names (Test 11)
Dialog read `d.status` / `d.member_id` / `d.contribution_base`, none of which exist on `gosi_api.get_employee_status()`'s actual response (`gosi_status`, `registration_date`, `last_contribution_month`). Dialog always showed "—" for every field and was always orange regardless of real status.
**Fix:** read the correct field names.

### 11. `public/js/employee.js` — Deregister-from-GOSI alert used green indicator (Test 11)
An offboarding action showing a green "success" alert reads wrong; test plan calls for orange.
**Fix:** changed to `indicator: "orange"`.

### 12. `public/js/employee.js` — "GOSI Estimate" button ignored the GOSI API enabled/disabled flag (Test 11 negative test)
Was always visible regardless of `gosi_api_enabled`, so disabling GOSI API integration didn't hide the full GOSI button group as the negative test expects.
**Fix:** moved it inside the same `Hr Suite Settings` gate as the other GOSI buttons.

### 13. Consolidated Work Permit Iqama's split JS files (organizational cleanup, Test 10)
`Work Permit Iqama` is hr_suite's own doctype, so it had no technical need to load a second, separate `public/js/work_permit_iqama.js` file (via a `hooks.py` `doctype_js` entry) on top of its own native controller at `doctype/work_permit_iqama/work_permit_iqama.js` — both were being loaded on the same form.
**Fix:** merged the Muqeem/Qiwa button code from `public/js/work_permit_iqama.js` into the doctype's own controller file (single `frappe.ui.form.on` block), deleted the now-redundant `public/js/work_permit_iqama.js`, and removed its entry from `hooks.py`'s `doctype_js`.
**Live-confirmed:** used Frappe's own `frappe.modules.get_doc_path()` to verify the doctype loads exactly this merged file, with the Muqeem buttons and employee-autofill/status logic both present and only one `frappe.ui.form.on` registration (not duplicated).

**Note — do NOT do this for `Salary Structure Assignment` or `Payroll Entry`:** both belong to `hrms` (module "Payroll"), not hr_suite. Their own native controllers are core HRMS files. `public/js/salary_structure_assignment.js` and `public/js/wps_payroll.js` (loaded via `doctype_js`) are the *correct and only appropriate* way to attach custom JS to doctypes hr_suite doesn't own — editing HRMS's own controller files directly would violate the standing rule against touching core app files, and would get overwritten on the next HRMS update anyway. `Nitaqat Record` is hr_suite's own doctype like Work Permit Iqama was, so it *could* get the same consolidation treatment if wanted later — not done yet.

## Known issues found but NOT fixed (flagged for a decision)

- **Employee Separation `termination_date` priority** (Test 14/18): computed as `resignation_letter_date or boarding_begins_on or Employee.relieving_date`. `boarding_begins_on` is a mandatory field on Employee Separation, so it's always populated by submit time — `Employee.relieving_date` is effectively unreachable in this fallback chain, contradicting the test's expectation that `termination_date = Employee.relieving_date`.
- **`hr_suite_employee_type` field only offers `"Saudi National"` / `"Expatriate"`** — no way to correctly mark an Emirati/Indian/Bahraini/Omani employee as a national of their own country through this field. This means the "national rate" branch of GCC statutory deductions can only ever be reached by (incorrectly) selecting "Saudi National" for a non-Saudi employee. Needs a decision: generalize the field's options, or add a separate per-country nationality concept.
- **Test 16's own expected day-counts (20/35) don't match the code's actual tiers** (full pay 0–30 days used, partial 75% 31–90, unpaid 91+) — this is the test plan's numbers being off, not a code bug. Use ~45 days for the partial-pay case and ~95 for the unpaid case when actually running this test.
- **Test 14 step 2's stated factor (2/3 at 5+ years resignation)** is wrong in the test text — the code correctly gives full gratuity (factor 1.0) at 5+ years per UAE Labour Law Art. 132.
